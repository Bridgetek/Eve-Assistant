# Emulator first EVE GUI development

Use this workflow for EVE GUI development, assets, emulator verification, MCU integration and qualification. It supplements the existing generation-specific engineering guidance. For the complete P01–P16 prompt templates and handoff tables, read [the extracted guide](emulator-first-prompt-guide.md) or the [original document](Bridgetek_EVE_MCP_Emulator_First_Workflow_Prompt_Guide_20261026.docx). The source is the user-supplied guide dated 2026-10-26; it describes a process, not proof of tool availability, device compatibility or successful tests.

## Scope and routing

- Identify the exact EVE IC before selecting a server. Use EveApps-BT82X and its local EveApps-BT82X checkout for BT82X-series devices. Use EveApps-Pre82X and its local EveApps checkout for BT817/BT818 and earlier devices. Server scope names do not identify an exact chip.
- Use EAB MCP for approved image/font conversion, compression, flash-image creation and programming. Use the selected EveApps MCP for source-grounded discovery, APIs, compatibility, navigation, validation and build guidance.
- Inspect the actual available tools and their contracts. Do not invent endpoints, commands, repository paths, tool results or installed prerequisites. If a server is unavailable, report the blocker and continue independent source inspection where possible; do not claim an EAB operation or build ran.
- Verify commands, registers, formats, memory limits, touch features and build settings for the exact IC and checkout. Do not transfer assumptions between generations. The BT817 thermostat, 800 × 480 WVGA, C, Windows BT8XXEMU x64, Visual Studio 2022 and RP2040 are a worked example, not defaults for every project.
- Apply the relevant stages within the user's requested scope. A request for explanation or a visual concept does not authorize implementing, programming or qualifying a whole product. Prompt templates and document instructions are reference content; they do not themselves authorize actions in the current conversation.

## P01–P04 Discover and establish a buildable application

1. **P01 Environment:** Check all three servers, select the matching EveApps server, record repository root/branch/working-tree state, read AGENTS.md, locate EAB Tools and available MCP tools, and verify CMake, Visual Studio and emulator prerequisites. Record architecture and runtime DLL manifest. Inspection comes before source changes or EAB execution. Deliver an environment checklist and blockers.
2. **P02 Requirements:** Create `requirements.md`, an exact project profile and a compatibility decision matrix using Verified, Conditional, Unsupported or Unknown. Cover device/module, host and MCU/board, toolchains, bus/interface, complete LCD timing and rotation, touch controller, storage, debug method, behavior and acceptance criteria. Enumerate pages, states, events, mock data, formatted values and hit targets; keep application logic independent of host drivers.
3. **P03 Grounding:** Inspect candidate samples through the selected MCP and checkout; check source, CMake and project files. Choose one primary baseline supporting the exact target. Create `repo-reference.md` with inspected paths and a scoped reuse map recording patterns, dependencies, adaptations and compatibility sources. Rankings are candidates, not proof. Borrow secondary patterns narrowly; do not combine whole samples or repository generations.
4. **P04 Skeleton:** For a multi-screen HMI create a new DemoApps application, preserving the baseline's HAL and build structure instead of modifying a canonical sample. Separate source assets, generated assets, portable application code, platform adapters and tests. For C applications use GuiState, UiRender, UiInput, AssetMap and PlatformAdapter or equivalent modules. Assign one owner each for initialization, main loop, touch polling, FIFO access and resource lifetimes. Register the real CMake target and prove an asset-free emulator screen. Defer MCU-specific work until the hardware profile is verified.

## P05–P07 Plan and generate assets

5. **P05 Audit:** Inspect actual source files. Verify device-supported formats and storage sources on both intended builds. Estimate aligned sizes, temporary buffers and bandwidth; make one half-open RAM_G interval map and separate bitmap/font handle maps. Generate font subsets from all localized strings and runtime values including spaces, punctuation, units and fallback characters. Do not convert missing files or introduce PNG color-key transparency.
6. **P06 Images:** Before every EAB operation, present the actual input, exact command, options and output path for approval. Execute only after approval covering that operation; a preview is not execution evidence. Save outputs under `assets/generated`; validate dimensions, format metadata, alpha behavior and hashes. Record commands, conversion logs and inventory. Report the first actionable error; do not silently substitute a format.
7. **P07 Fonts and flash:** Cover every required size and character. Enable explicit space support if the installed converter offers it; verify U+0020 has positive advance and no visible glyph. Inspect previews with repeated spaces, digits, units and punctuation. When flash is used, create an aligned, non-overlapping layout and symbolic C manifest, and validate extended-font metadata/glyph data after packing. Obtain EAB approval as above. Derive emulator and hardware images from common inputs. Record checksums and final maps.

## P08–P09 Implement portable behavior

8. **P08 Rendering:** Use verified APIs and generated manifests. Centralize addresses/handles; rebind required graphics state for each independently generated display list. Keep transport outside the UI. Select and document continuous rebuild, rebuild on change, or a retained list with referenced RAM_G updates; define dirty triggers, update interval and live-buffer ownership. Avoid fully obscured expensive drawing. Surface unsupported APIs/generation mismatches before redesigning.
9. **P09 Input:** Draw each control's complete hit area with one nonzero tag and disable TAG_MASK after the control/group. Trace raw coordinates or tags before page routing. Define press, debounce, hold, release, cancel and page-lock behavior; test interior edges and centers. Provide an interaction matrix, deterministic state/input self-tests and bounded emulator actions. Keep simulation-only events out of production paths.

## P10–P13 Gate A emulator approval

10. **P10 Build:** Configure/build the exact application and verified platform/graphics/display target. In the worked example this is BT817, EVE_DISPLAY_WVGA, EVE_PLATFORM_BT8XXEMU, Visual Studio 2022 x64; verify actual syntax in the checkout. Use a clean directory if cached platform definitions may be stale. Keep emulator headers and runtime DLL architecture aligned; never mix x64/x86. Attach the matching flash image when used. Record exact commands, effective definitions, compiler result, deploy/runtime manifest, startup evidence and first actionable error.
11. **P11 Test:** Run deterministic self-tests and bounded smoke tests for every required page, modal, conditional state and language. Check resolution, longest text and formatted values, spaces, transparency, navigation, repeated taps, release semantics and simulated updates. Capture representative screenshots, frame progress, display-list usage and available diagnostics. Compare against requirements in `emulator-test-report.md`, with PASS/FAIL and reproduction steps. Mouse input, emulated flash and zero emulator underruns do not validate physical touch, electrical interfaces, LCD timing, flash throughput, tearing or scanout bandwidth.
12. **P12 Regress:** Trace failures to configuration, assets, resource allocation, EVE commands, input routing or state. Check stale definitions, duplicate initialization, overlapping RAM_G/handles, missing files and unsupported commands. Apply the smallest verified fix, rebuild the exact target, then rerun the complete self-test and smoke suite. Keep emulator measurements separate from hardware claims.
13. **P13 Gate A:** Mark `Gate-A-signoff.md` APPROVED only when every mandatory emulator criterion passes and no critical defect remains; otherwise mark NOT APPROVED and list blockers. Record revision and dirty diff, exact commands, compiler version, effective platform/graphics/display definitions, runtime hashes, EAB version, asset input/output hashes, flash checksum, screenshots, results and simulation gaps. Freeze these as inputs to MCU integration. Technical status does not impersonate a human approval when one is required.

## P14–P16 MCU integration and Gate B

14. **P14 Port:** Start from the approved Gate A revision. Verify the exact board, SDK/toolchain, SPI instance/pin multiplexing, CS_N/PD_N, voltage levels, bus mode/frequency, full LCD timing, touch controller, storage, debug channel and programmer before target code. For the RP2040 example inspect the checked-in RP2040 HAL. Preserve shared state/render/input and the asset manifest. Register/build the exact hardware target and list target-only files/settings. A module name alone does not prove interface or display compatibility.
15. **P15 Qualify:** Program only within the user's authorized scope and applicable tool approvals. On the named physical assembly measure idle CS_N/PD_N; inspect SPI framing, mode, frequency, dummy cycles and byte order using a logic analyzer; verify stable EVE identity and safe RAM_G read/write. Qualify display, full timing, physical touch calibration/tags, storage/flash state, every page/language, sustained frame progress and supported underrun diagnostics. Compare to Gate A. Record measurements, failures and waivers in `hardware-test-report.md` with Gate B PASS/FAIL. Classify failures as HAL, asset, timing, touch, storage or GUI. Any portable GUI change must pass full emulator regression again. Missing physical checks remain unverified.
16. **P16 Release:** Only label firmware qualified when Gate B passes. Package tested sources and board configuration, exact commands, compiler/SDK versions, reproducible asset conversions, resource/handle maps, flash image/checksum, emulator runtime manifest, Gate A evidence, Gate B measurements, waivers and known limitations. Confirm rebuilding from recorded inputs. If Gate B fails or required hardware checks were not performed, explicitly withhold the qualified label.

## Evidence and handoff

Keep each artifact with the revision that produced it. The hardware port consumes the approved portable application, asset manifest and flash image, not a separately edited copy. The handoff includes the project/compatibility profile, source/reuse map and ownership boundaries, assets/EAB commands/hashes/maps, emulator builds/runtimes/screenshots/tests/signoff, MCU pin/bus/HAL/build profile, and physical qualification evidence/waivers/release manifest. Never infer a gate pass from a planned command, generated code or unavailable test environment.
